# Практическое занятие №6

## Реализация защиты от CSRF/XSS и работа с secure cookies

## Цель

Освоить базовые способы защиты Go web-приложения от CSRF и XSS, а также безопасную настройку cookie для хранения идентификатора сессии.

## Задание

Реализовано учебное web-приложение с маршрутами:

- `GET /login` — имитация входа, создание `session_id` и `csrf_token`, установка cookie;
- `GET /profile` — HTML-форма изменения имени пользователя;
- `POST /profile` — обновление имени после проверки cookie и CSRF-токена;
- `GET /hello` — безопасное отображение имени пользователя через HTML-шаблон.

Профили пользователей хранятся в памяти приложения. `session_id` и `csrf_token` генерируются через криптографически стойкий `crypto/rand`.

## Cookie

Приложение устанавливает cookie `session_id` с атрибутами:

- `HttpOnly: true` — запрещает чтение cookie из JavaScript;
- `SameSite: Lax` — снижает риск CSRF в межсайтовых сценариях;
- `Path: /` — cookie доступна для всех маршрутов приложения;
- `Secure: false` — допустимо только для локального HTTP-запуска.

Для запуска по HTTPS нужно установить `Secure: true`, чтобы браузер отправлял cookie только по защищённому соединению.

## Проверка `/login`

```bash
curl -i -c cookies.txt http://localhost:8080/login
```

Ожидается ответ `302 Found`, заголовок `Set-Cookie` с `session_id` и перенаправление на `/profile`.

## Проверка `/profile`

```bash
curl -i -b cookies.txt http://localhost:8080/profile
```

Ожидается HTML-форма профиля со скрытым полем `csrf_token`.

## Проверка успешного `POST /profile`

Скопируйте значение `csrf_token` из HTML-формы и отправьте запрос:

```bash
curl -i -b cookies.txt \
  -d "name=Иван" \
  -d "csrf_token=ВАШ_CSRF_TOKEN" \
  http://localhost:8080/profile
```

Ожидается ответ `302 Found` с перенаправлением на `/hello`.

## Проверка `/hello`

```bash
curl -i -b cookies.txt http://localhost:8080/hello
```

Ожидается HTML-страница с приветствием и текущим именем пользователя.

## Проверка CSRF-ошибки

Запрос без CSRF-токена должен быть отклонён:

```bash
curl -i -b cookies.txt \
  -d "name=Иван" \
  http://localhost:8080/profile
```

Ожидается:

```text
HTTP/1.1 403 Forbidden
invalid csrf token
```

## Проверка безопасного отображения XSS-строки

В форме `/profile` введите строку:

```html
<script>alert('xss')</script>
```

После сохранения страница `/hello` должна показать эту строку как обычный текст. Окно `alert` не должно открываться, потому что вывод выполняется через `html/template`, который экранирует HTML.

## Опасный XSS-пример

Такой подход приведён только как демонстрация риска. Он не используется в рабочих обработчиках:

```go
func unsafeHello(w http.ResponseWriter, name string) {
	html := "<html><body><h1>Здравствуйте, " + name + "!</h1></body></html>"
	w.Header().Set("Content-Type", "text/html; charset=utf-8")
	_, _ = w.Write([]byte(html))
}
```

Если `name` содержит HTML или JavaScript, браузер может интерпретировать его как часть страницы. Поэтому пользовательский ввод нельзя вставлять в HTML через конкатенацию строк.

## Ответы на контрольные вопросы

1. **Что такое CSRF?**

   CSRF — это атака, при которой браузер пользователя отправляет запрос на сайт без осознанного действия самого пользователя. Проблема возникает из-за того, что браузер автоматически прикладывает cookies к запросам, и сервер может принять такой запрос как настоящий.

2. **Почему CSRF особенно связан с cookie-аутентификацией?**

   При cookie-аутентификации браузер сам добавляет cookie к запросу на соответствующий сайт. Если сервер проверяет только наличие cookie, злоумышленник может попытаться заставить браузер пользователя отправить нежелательный запрос. Поэтому для важных действий нужно проверять дополнительный CSRF-токен.

3. **Как CSRF-токен помогает защитить форму?**

   CSRF-токен генерируется сервером и добавляется в HTML-форму. При отправке формы сервер проверяет, что токен из формы совпадает с токеном, который был выдан пользователю. Злоумышленник не знает этот токен, поэтому не может корректно подделать запрос.

4. **Что такое XSS?**

   XSS — это атака, при которой вредоносный HTML или JavaScript попадает на страницу и выполняется в браузере пользователя. Обычно это происходит, если приложение выводит пользовательский ввод как готовую HTML-разметку без экранирования.

5. **Чем CSRF отличается от XSS?**

   CSRF использует доверие сервера к браузеру пользователя и его cookie.  
   XSS использует доверие браузера к странице, которую вернул сервер. При CSRF злоумышленник пытается отправить действие от имени пользователя, а при XSS — внедрить код в страницу.

6. **Зачем нужен атрибут HttpOnly у cookie?**

   `HttpOnly` запрещает JavaScript-коду на странице читать cookie через `document.cookie`. Это снижает риск кражи session cookie при XSS-уязвимости.

7. **Для чего используется атрибут SameSite?**

   `SameSite` ограничивает отправку cookie при переходах и запросах с других сайтов. Это помогает снизить риск CSRF-атак, потому что браузер не всегда будет прикладывать cookie к межсайтовым запросам.

8. **Зачем нужен атрибут Secure у cookie?**

   `Secure` разрешает отправлять cookie только по HTTPS. Это защищает cookie от передачи по незащищённому HTTP-каналу. В локальной учебной среде без HTTPS этот атрибут можно временно не включать, но в production он должен использоваться.

9. **Почему для вывода пользовательских данных используется `html/template`?**

   `html/template` автоматически экранирует пользовательские данные при вставке в HTML. Поэтому строка вроде `<script>alert('xss')</script>` отображается как текст, а не выполняется браузером как JavaScript-код.

10. **Почему нельзя выводить пользовательский ввод через ручную конкатенацию HTML-строк?**

    При ручной конкатенации можно случайно вставить пользовательский ввод прямо в HTML-разметку. Если пользователь передаст JavaScript-код, браузер может выполнить его. Это создаёт XSS-уязвимость.

11. **Почему CSRF-токены нужно генерировать случайно и достаточно длинными?**

    Если токен легко угадать, злоумышленник сможет подставить его в поддельный запрос. Поэтому токены нужно генерировать через криптографически стойкий источник случайности, например `crypto/rand`, и делать достаточно длинными.

12. **Какие меры защиты используются в этой работе?**

    В этой работе используются secure cookies с атрибутами `HttpOnly`, `SameSite` и `Path`, CSRF-токен для проверки формы, генерация `session_id` и `csrf_token` через `crypto/rand`, а также безопасный вывод пользовательских данных через `html/template`.
