# Практическая работа №3. Логирование с помощью zap

## Цель

Освоить структурированное логирование в HTTP-сервисе на Go с использованием библиотеки `zap`: логировать входящие запросы, успешные операции и ошибки с полезными полями контекста.

## Задание

Реализовать учебный HTTP-сервис с маршрутами:

- `GET /health` — проверка работоспособности сервиса;
- `GET /students/{id}` — получение информации о студенте по идентификатору.

Сервис должен логировать HTTP-метод, путь, код ответа, длительность обработки и `request_id`, а также фиксировать успешную выдачу студента и ошибки.

## Примеры curl-запросов

Проверка состояния сервиса:

```bash
curl http://localhost:8080/health
```

Ожидаемый ответ:

```json
{"status":"ok"}
```

Получение студента:

```bash
curl http://localhost:8080/students/1
```

Ожидаемый ответ:

```json
{"id":1,"full_name":"Иванов Иван Иванович","group":"ИВБО-01-25","email":"ivanov@example.com"}
```

Ошибка в идентификаторе:

```bash
curl -i http://localhost:8080/students/abc
```

Ожидаемый статус: `400 Bad Request`.

Отсутствующий студент:

```bash
curl -i http://localhost:8080/students/999
```

Ожидаемый статус: `404 Not Found`.

Неподдерживаемый метод:

```bash
curl -i -X POST http://localhost:8080/health
```

Ожидаемый статус: `405 Method Not Allowed`.

## Ответы на контрольные вопросы

1. **Зачем backend-приложению нужно логирование?**

   Логирование нужно для того, чтобы понимать, что происходит внутри приложения во время работы. По логам можно увидеть запуск сервиса, входящие запросы, ошибки, время обработки, возвращённые статусы и важные внутренние события. Без логов сложно разбирать ошибки и сопровождать backend-сервис.

2. **Чем обычный текстовый лог отличается от структурированного?**

   Обычный текстовый лог — это просто строка с сообщением. Его удобно читать глазами, но сложнее автоматически фильтровать и анализировать.  
   Структурированный лог содержит не только сообщение, но и отдельные поля, например `method`, `path`, `status_code`, `duration`, `request_id`. Такие логи проще искать, фильтровать и передавать в системы наблюдаемости.

3. **Что означает structured logging?**

   Structured logging — это подход, при котором каждое событие записывается как структурированная запись с набором полей в формате ключ-значение. Например, вместо одной строки `"request completed"` лог содержит отдельные данные: метод запроса, путь, код ответа и длительность обработки.

4. **Какие уровни логирования используются в этой работе?**

   В работе используются уровни `debug`, `info`, `warn` и `error`.  
   `debug` подходит для подробной отладочной информации, `info` — для обычных рабочих событий, `warn` — для ситуаций с ошибками клиента или нестандартным поведением, `error` — для серьёзных ошибок приложения.

5. **Почему полезно логировать HTTP-метод, путь и статус ответа?**

   Эти поля позволяют быстро понять, какой запрос пришёл в приложение и чем он завершился. Например, по `method` и `path` можно увидеть вызванный endpoint, а по `status_code` — успешным был запрос или завершился ошибкой.

6. **Зачем в лог добавляют время выполнения запроса?**

   Время выполнения помогает понять, насколько быстро приложение обрабатывает запросы. Если какой-то endpoint начинает работать медленно, поле `duration` позволяет это заметить и найти проблемный участок.

7. **Почему логирование ошибок должно содержать дополнительный контекст?**

   Одного сообщения об ошибке часто недостаточно. Контекст помогает понять, при каком запросе произошла ошибка, какой был путь, какой id передали, какой статус вернулся и сколько времени заняла обработка. Без такого контекста ошибку сложнее воспроизвести и исправить.

8. **В чём практическое преимущество zap?**

   `zap` позволяет писать быстрые структурированные логи с уровнями и полями. Он хорошо подходит для backend-приложений, потому что даёт удобный JSON-формат, поддерживает `debug`, `info`, `warn`, `error` и позволяет добавлять к сообщениям полезный контекст.

9. **Что означает maintenance mode у logrus?**

   Maintenance mode означает, что библиотека в основном поддерживается и исправляется, но новые возможности активно не развиваются. То есть `logrus` ещё можно встретить в проектах, но для новых сервисов чаще выбирают более современные варианты, например `zap` или `slog`.

10. **Почему structured logging особенно важен для микросервисов и backend API?**

    В микросервисной архитектуре запрос может проходить через несколько сервисов, поэтому важно быстро понимать, где именно возникла ошибка. Структурированные логи позволяют искать события по `request_id`, `path`, `status_code`, имени сервиса и другим полям. Это упрощает диагностику и сопровождение backend API.
