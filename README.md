# Практическая работа №5

## Цель

Освоить запуск backend-приложения на Go по HTTPS и безопасную работу с PostgreSQL без SQL-инъекций.

## Задание

Реализовано учебное приложение, которое:

- запускает HTTPS-сервер на порту `8443`;
- использует self-signed TLS-сертификат из каталога `certs`;
- подключается к PostgreSQL;
- предоставляет маршруты `GET /health` и `GET /students?id=...`;
- получает студента безопасно через prepared statement;
- содержит демонстрационный небезопасный SQL-запрос, который не используется в обработчиках.

## Запуск PostgreSQL

Вариант через Docker Compose:

```bash
docker compose up -d postgres
```

При первом запуске контейнера будет создана база `study_security`, а файл `sql/init.sql` создаст таблицу `students` и добавит начальные данные.

Если PostgreSQL уже установлен локально, базу можно создать вручную:

```bash
createdb study_security
psql "postgres://postgres:postgres@localhost:5432/study_security?sslmode=disable" -f sql/init.sql
```

## Генерация сертификата

В проект уже добавлен учебный self-signed сертификат для `localhost`. При необходимости его можно пересоздать:

```bash
openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout certs/server.key \
  -out certs/server.crt \
  -days 365 \
  -subj "/CN=localhost" \
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"
```

## Запуск HTTPS-сервера

По умолчанию приложение использует строку подключения:

```text
postgres://postgres:postgres@localhost:5432/study_security?sslmode=disable
```

Запуск:

```bash
go run ./cmd/server
```

Ожидаемый лог:

```text
HTTPS server started on https://localhost:8443
```

Параметры можно переопределить переменными окружения:

```bash
SERVER_ADDR=:8443
TLS_CERT_FILE=certs/server.crt
TLS_KEY_FILE=certs/server.key
POSTGRES_DSN=postgres://postgres:postgres@localhost:5432/study_security?sslmode=disable
```

## Проверка

Проверка состояния сервера:

```bash
curl -k https://localhost:8443/health
```

Ожидаемый ответ:

```json
{"scheme":"https","status":"ok"}
```

Получение студента:

```bash
curl -k "https://localhost:8443/students?id=1"
```

Ожидаемый ответ:

```json
{"id":1,"full_name":"Иванов Иван Иванович","study_group":"ИВБО-01-25","email":"ivanov@example.com"}
```

Проверка отсутствующего студента:

```bash
curl -k "https://localhost:8443/students?id=999"
```

Ожидаемый результат: статус `404 Not Found`.

Проверка некорректного ввода:

```bash
curl -k "https://localhost:8443/students?id=1%20OR%201=1"
```

Ожидаемый результат: статус `400 Bad Request`.

## Защита от SQL-инъекций

В `internal/student/repo.go` специально оставлен небезопасный демонстрационный пример:

```go
query := "SELECT id, full_name, study_group, email FROM students WHERE id = " + rawID
```

Такой код опасен, потому что пользовательский ввод становится частью SQL-текста.

В рабочем обработчике этот метод не используется. Запрос к студенту выполняется через prepared statement:

```go
stmt, err := repo.PrepareGetByID()
```

Сам SQL-запрос использует placeholder PostgreSQL:

```go
"SELECT id, full_name, study_group, email FROM students WHERE id = $1"
```

Значение `id` передается отдельно через `stmt.QueryRow(id)`, поэтому база данных воспринимает ввод как значение параметра, а не как SQL-код.

## Ответы на контрольные вопросы

1. **Чем HTTP отличается от HTTPS?**

   HTTP передаёт данные без шифрования, поэтому содержимое запроса и ответа потенциально может быть перехвачено или изменено. HTTPS использует TLS и обеспечивает защищённое соединение между клиентом и сервером.

2. **Какую роль выполняет TLS в защищённом соединении?**

   TLS отвечает за шифрование данных, проверку подлинности сервера и защиту передаваемой информации от подмены. Благодаря TLS клиент и сервер могут обмениваться данными по защищённому каналу.

3. **Что такое TLS-сертификат?**

   TLS-сертификат — это файл с данными, которые используются для подтверждения подлинности сервера и установления защищённого соединения. Сертификат содержит информацию о владельце, публичный ключ и другие служебные данные.

4. **Что делает `tls.LoadX509KeyPair`?**

   `tls.LoadX509KeyPair` загружает пару TLS-файлов: сертификат и приватный ключ. В Go эта функция используется для подготовки HTTPS-сервера к работе с защищёнными соединениями.

5. **Почему self-signed certificate подходит для локальной учебной среды, но не для публичного production-сервиса?**

   Самоподписанный сертификат подходит для локальной проверки, потому что позволяет протестировать сам механизм HTTPS без покупки или выпуска настоящего сертификата. Но для публичного production-сервиса он не подходит, потому что браузеры и клиенты не доверяют такому сертификату автоматически и показывают предупреждение безопасности.

6. **Что такое SQL-инъекция?**

   SQL-инъекция — это уязвимость, при которой пользовательский ввод попадает прямо в SQL-запрос и может изменить его структуру. Из-за этого злоумышленник может попытаться получить лишние данные, изменить условие запроса или выполнить нежелательные действия в базе данных.

7. **Почему конкатенация строки SQL с пользовательским вводом опасна?**

   При конкатенации пользовательский ввод становится частью SQL-кода. Если вместо обычного значения передать фрагмент SQL, он может быть выполнен как часть запроса. Например, условие может превратиться в `id = 1 OR 1=1`, и запрос начнёт работать не так, как ожидалось.

8. **Что такое parameterized query?**

   Parameterized query — это SQL-запрос, в котором текст запроса и значения параметров передаются отдельно. Пользовательский ввод не вставляется напрямую в строку SQL, а передаётся как значение параметра. Это защищает запрос от SQL-инъекций.

9. **Что такое prepared statement?**

   Prepared statement — это заранее подготовленный SQL-запрос с placeholder-ами для параметров. СУБД разбирает и сохраняет структуру запроса, а значения подставляются отдельно при выполнении. Такой подход удобен для безопасного и повторного выполнения однотипных запросов.

10. **Почему placeholder syntax может отличаться в разных СУБД и драйверах?**

    Разные СУБД и драйверы используют разные форматы placeholder-ов. Например, в PostgreSQL через драйвер `pq` используется синтаксис `$1`, `$2` и так далее. В других базах могут использоваться `?` или именованные параметры. Поэтому при написании SQL-запросов нужно учитывать конкретный драйвер и СУБД.
