# Практическое занятие №1

## Разделение монолита на 2 микросервиса. Взаимодействие через HTTP

Цель работы: освоить базовый подход к разделению backend-приложения на два самостоятельных Go-сервиса и организовать обмен JSON-данными между ними по HTTP.

## Архитектура

Проект состоит из двух независимых сервисов:

- `user-service` хранит пользователей в памяти и отдаёт их по HTTP.
- `order-service` хранит заказы в памяти, отдаёт обычный заказ и агрегированный ответ `заказ + пользователь`.

`order-service` при запросе `/orders/{id}/full` обращается к `user-service` по адресу `http://localhost:8081/users/{user_id}`.

## user-service

Порт: `8081`

Endpoint:

```http
GET /users/{id}
```

Пример ответа:

```json
{"id":1,"name":"Иван Иванов","email":"ivan@example.com"}
```

Ошибки:

- `400 Bad Request` при некорректном `id`;
- `404 Not Found` если пользователь не найден;
- `405 Method Not Allowed` если HTTP-метод не поддерживается.

## order-service

Порт: `8082`

Endpoints:

```http
GET /orders/{id}
GET /orders/{id}/full
```

Пример обычного заказа:

```json
{"id":101,"user_id":1,"item":"Ноутбук","price":79990}
```

Пример агрегированного ответа:

```json
{
  "order": {
    "id": 101,
    "user_id": 1,
    "item": "Ноутбук",
    "price": 79990
  },
  "user": {
    "id": 1,
    "name": "Иван Иванов",
    "email": "ivan@example.com"
  }
}
```

Если `user-service` недоступен при запросе `/orders/{id}/full`, `order-service` возвращает `502 Bad Gateway` и не завершает работу аварийно.

## Запуск

В первом терминале:

```bash
cd user-service
go run ./cmd/server
```

Ожидаемый лог:

```text

```

Во втором терминале:

```bash
cd order-service
go run ./cmd/server
```

Ожидаемый лог:

```text
order-service started on :8082
```

## Проверка через curl

Пользователь:

```bash
curl http://localhost:8081/users/1
```

Заказ:

```bash
curl http://localhost:8082/orders/101
```

Агрегированный ответ:

```bash
curl http://localhost:8082/orders/101/full
```

Ошибка внешнего сервиса:

```bash
curl -i http://localhost:8082/orders/101/full
```

Для этой проверки нужно остановить `user-service`. Ожидается статус `502 Bad Gateway`.

## Ответы на контрольные вопросы

1. **Чем монолит отличается от микросервисной архитектуры?**

   Монолит — это приложение, где вся логика находится в одном процессе и обычно запускается как один сервер. В микросервисной архитектуре система разделяется на несколько самостоятельных сервисов, каждый из которых отвечает за свою часть логики и взаимодействует с другими сервисами по сети.

2. **Почему разделение системы на сервисы не всегда является лучшим решением?**

   Микросервисы дают гибкость, но одновременно усложняют разработку. Нужно учитывать сетевые ошибки, таймауты, разные порты, отдельный запуск сервисов, мониторинг и согласованность данных. Для маленького проекта монолит часто проще и удобнее.

3. **Какую ответственность в этой работе несёт user-service, а какую — order-service?**

   `user-service` отвечает за хранение и выдачу информации о пользователях.
   `order-service` отвечает за хранение и выдачу заказов. Когда нужно получить заказ вместе с пользователем, `order-service` обращается к `user-service` по HTTP и формирует общий ответ.

4. **Почему в микросервисной архитектуре важно обрабатывать таймауты и сетевые ошибки?**

   Потому что сервисы взаимодействуют по сети, а сеть может быть нестабильной. Другой сервис может быть выключен, отвечать слишком долго или вернуть ошибку. Если не обрабатывать такие ситуации, один проблемный сервис может привести к зависанию или неправильной работе другого сервиса.

5. **Что означает статус 502 Bad Gateway в контексте взаимодействия сервисов?**

   В этой работе статус `502 Bad Gateway` означает, что `order-service` не смог получить корректный ответ от `user-service`. Например, `user-service` не запущен, недоступен по нужному порту или вернул некорректный ответ.

6. **Почему один сервис не должен напрямую обращаться к внутренним структурам кода другого сервиса?**

   Потому что каждый микросервис должен быть самостоятельным. Если `order-service` начнёт напрямую использовать внутренний код `user-service`, сервисы снова станут сильно связанными между собой. Правильнее взаимодействовать через внешний контракт — например, через HTTP API.

7. **Какие преимущества даёт разделение на сервисы при росте проекта?**

   Разделение позволяет независимо развивать, запускать и масштабировать отдельные части системы. Например, если нагрузка больше идёт на заказы, можно масштабировать только `order-service`, не трогая `user-service`. Также разным командам проще работать над разными частями проекта.

8. **Какие новые сложности появляются после такого разделения?**

   Появляются сетевые вызовы, необходимость обрабатывать недоступность сервисов, следить за портами и адресами, проектировать API между сервисами, запускать несколько процессов и отдельно проверять их взаимодействие.


## Вывод

В работе реализовано разделение учебного приложения на два независимых Go-сервиса. `order-service` агрегирует собственные данные с данными из `user-service` через HTTP, а оба сервиса обрабатывают успешные и ошибочные сценарии.
