# Практическая работа №10

## Цель

Освоить горизонтальное масштабирование backend-сервиса через запуск двух экземпляров приложения `tasks` и распределение запросов между ними с помощью NGINX Load Balancer.

## Задание

Реализовать учебный стенд, в котором клиент обращается только к NGINX на порту `8080`, а NGINX проксирует запросы во внутренние реплики `tasks_1` и `tasks_2`.

Сервис `tasks` должен:

- читать `APP_PORT` и `INSTANCE_ID` из переменных окружения;
- отдавать `GET /health`;
- отдавать `GET /v1/tasks`;
- отдавать `GET /whoami`;
- добавлять заголовок `X-Instance-ID` во все ответы.

## Запуск стенда

```bash
cd deploy/lb
docker compose up -d --build
docker compose ps
```

После запуска внешний доступ есть только через NGINX:

```text
http://localhost:8080
```

Реплики `tasks_1` и `tasks_2` не пробрасывают порты наружу.

## Проверка /health

```bash
curl -i http://localhost:8080/health
```

Ожидается:

- статус `200 OK`;
- JSON с `status: ok`;
- заголовок `X-Instance-ID`.

Пример:

```text
HTTP/1.1 200 OK
X-Instance-ID: tasks-1
```

## Проверка списка задач

```bash
curl -i http://localhost:8080/v1/tasks
```

Ожидается JSON-массив задач и заголовок `X-Instance-ID`.

## Проверка балансировки

```bash
for i in {1..10}; do
  curl -s -i http://localhost:8080/v1/tasks | grep X-Instance-ID
done
```

В ответах должны встречаться обе реплики:

```text
X-Instance-ID: tasks-1
X-Instance-ID: tasks-2
```

## Проверка /whoami

```bash
curl -i http://localhost:8080/whoami
```

Пример ответа:

```json
{"instance":"tasks-1"}
```

## Проверка заголовка X-Instance-ID

```bash
curl -s -D - http://localhost:8080/health -o /dev/null | grep X-Instance-ID
```

Ожидается один из вариантов:

```text
X-Instance-ID: tasks-1
```

или:

```text
X-Instance-ID: tasks-2
```

## Проверка остановки одной реплики

Остановить первую реплику:

```bash
docker compose stop tasks_1
```

Проверить, что сервис продолжает отвечать через NGINX:

```bash
for i in {1..5}; do
  curl -s -i http://localhost:8080/v1/tasks | grep X-Instance-ID
done
```

Ожидается, что ответы идут от оставшейся реплики:

```text
X-Instance-ID: tasks-2
```

## Возврат реплики в работу

```bash
docker compose start tasks_1
```

После возврата повторить проверку балансировки:

```bash
for i in {1..10}; do
  curl -s -i http://localhost:8080/v1/tasks | grep X-Instance-ID
done
```

Снова должны встречаться `tasks-1` и `tasks-2`.

## Остановка стенда

```bash
docker compose down
```
## Ответы на контрольные вопросы

1. **Чем горизонтальное масштабирование отличается от вертикального?**

   Вертикальное масштабирование — это увеличение ресурсов одного сервера или одного экземпляра приложения: больше CPU, больше RAM, более мощная машина.

   Горизонтальное масштабирование — это запуск нескольких экземпляров одного и того же сервиса. В этой работе вместо одного сервиса `tasks` запускаются две реплики: `tasks_1` и `tasks_2`.

2. **Зачем нужен Load Balancer?**

   Load Balancer принимает входящие запросы от клиента и распределяет их между несколькими backend-экземплярами. Для клиента система выглядит как один сервис, хотя внутри работает несколько реплик приложения.

3. **Какую роль в этой работе выполняет NGINX?**

   В этой работе NGINX выполняет роль reverse proxy и балансировщика нагрузки. Он принимает запросы на внешнем порту `8080` и перенаправляет их на одну из реплик сервиса `tasks`: `tasks_1` или `tasks_2`.

4. **Что такое upstream в конфигурации NGINX?**

   `upstream` — это блок конфигурации NGINX, в котором описывается группа backend-серверов. В этой работе в upstream `tasks_backend` указаны две реплики сервиса: `tasks_1:8082` и `tasks_2:8082`.

5. **Почему реплики сервиса не должны пробрасывать порты наружу?**

   Клиент должен обращаться к системе через Load Balancer, а не напрямую к отдельным репликам. Если открыть порты каждой реплики наружу, клиент сможет обходить NGINX, и балансировка потеряет смысл.

6. **Зачем нужен заголовок `X-Instance-ID`?**

   Заголовок `X-Instance-ID` помогает понять, какой именно экземпляр сервиса обработал запрос. В этой работе по нему можно проверить, что запросы действительно распределяются между `tasks-1` и `tasks-2`.

7. **Что произойдёт, если остановить одну из реплик?**

   Если остановить одну реплику, NGINX должен продолжить направлять запросы на оставшийся доступный экземпляр. Например, если остановить `tasks_1`, запросы должны продолжить обрабатываться через `tasks_2`.

8. **Почему для горизонтального масштабирования сервис желательно делать stateless?**

   Stateless-сервис не хранит важное пользовательское состояние внутри памяти конкретного экземпляра. Это важно, потому что разные запросы одного клиента могут попасть на разные реплики. Если состояние хранится только внутри одной реплики, при переключении на другую реплику данные могут потеряться.

9. **Для чего прокидываются заголовки `X-Request-ID` и `X-Forwarded-For`?**

   `X-Request-ID` помогает отслеживать конкретный запрос в логах разных сервисов.
   `X-Forwarded-For` передаёт backend-сервису информацию об исходном IP-адресе клиента, потому что напрямую сервис видит запрос от NGINX, а не от реального клиента.

10. **Почему балансировщик нагрузки повышает отказоустойчивость системы?**

    Если в системе работает несколько реплик, отказ одной из них не обязательно приводит к полной недоступности приложения. Load Balancer может продолжить направлять запросы на оставшиеся рабочие экземпляры. Поэтому система становится устойчивее к сбоям отдельных сервисов.

11. **Почему при масштабировании важно проверять `/health`?**

    Endpoint `/health` позволяет быстро понять, доступен ли конкретный экземпляр приложения. В реальных системах такие проверки используются балансировщиками и оркестраторами, чтобы не отправлять трафик на неработающие экземпляры.

12. **Что показывает проверка несколькими запросами подряд к `/whoami`?**

    Проверка `/whoami` несколькими запросами подряд показывает, между какими репликами распределяется трафик. Если в ответах поочерёдно встречаются `tasks-1` и `tasks-2`, значит балансировка работает.
