# Практическая работа N12: REST и GraphQL для Task

## Цель

Реализовать один и тот же функционал для сущности `Task` двумя способами: через REST API и через GraphQL API. На одном пользовательском сценарии нужно сравнить количество запросов, состав данных, обработку ошибок, документирование, тестирование и кэширование.

## Единый сценарий сравнения

Экран списка задач использует поля `id`, `title`, `done`. Экран деталей использует поля `id`, `title`, `description`, `done`. Действия изменения данных: создание новой задачи и обновление признака `done`.

Оба API работают с одной моделью `Task`, общим in-memory repository и общим service layer. Поэтому REST и GraphQL видят одинаковые данные в рамках одного запущенного процесса.

## Структура проекта

```text
pz12-rest-vs-graphql/
├── cmd/server/              # запуск общего REST + GraphQL сервера
├── graph/                   # схема и резолверы gqlgen

├── internal/task/           # модель, repository и service layer
├── gqlgen.yml               # конфигурация gqlgen

└── README.md
```

## Запуск

```bash
cd pz12-rest-vs-graphql
go run ./cmd/server
```

По умолчанию сервер запускается на порту `8082`.

REST API доступен по адресу:

```text
http://localhost:8082/v1/tasks
```

GraphQL endpoint доступен по адресу:

```text
http://localhost:8082/query
```

GraphQL Playground доступен по адресу:

```text
http://localhost:8082/
```

## REST-примеры

Получить список задач:

```bash
curl -s http://localhost:8082/v1/tasks
```

Получить одну задачу:

```bash
curl -s http://localhost:8082/v1/tasks/t_001
```

Создать задачу:

```bash
curl -s -X POST http://localhost:8082/v1/tasks \
  -H "Content-Type: application/json" \
  -d '{"title":"Сравнить REST и GraphQL","description":"Практическая работа N12"}'
```

Обновить `done`:

```bash
curl -s -X PATCH http://localhost:8082/v1/tasks/t_001 \
  -H "Content-Type: application/json" \
  -d '{"done":true}'
```

Пример ошибки:

```bash
curl -i http://localhost:8082/v1/tasks/unknown
```

Ожидаемый результат: HTTP `404 Not Found` и тело `{"error":"task not found"}`.

## GraphQL-примеры

Список задач только с полями для экрана списка:

```graphql
query {
  tasks {
    id
    title
    done
  }
}
```

Детали задачи:

```graphql
query GetTask($id: ID!) {
  task(id: $id) {
    id
    title
    description
    done
  }
}
```

Переменные:

```json
{
  "id": "t_001"
}
```

Создание задачи:

```graphql
mutation Create($input: CreateTaskInput!) {
  createTask(input: $input) {
    id
    title
    description
    done
  }
}
```

Переменные:

```json
{
  "input": {
    "title": "Сравнить REST и GraphQL",
    "description": "Практическая работа N12"
  }
}
```

Обновление `done`:

```graphql
mutation Update($id: ID!, $input: UpdateTaskInput!) {
  updateTask(id: $id, input: $input) {
    id
    title
    description
    done
  }
}
```

Переменные:

```json
{
  "id": "t_001",
  "input": {
    "done": true
  }
}
```

Пример ошибки:

```graphql
query {
  task(id: "unknown") {
    id
    title
  }
}
```

Ожидаемый результат: HTTP-ответ обычно остаётся `200 OK`, а ошибка находится в поле `errors` JSON-ответа.

## Сравнение

| Критерий | REST | GraphQL |
|---|---|---|
| Количество запросов | Для сценария список -> детали -> обновление нужно 3 запроса: `GET`, `GET`, `PATCH`. | Для того же сценария нужно 3 операции: query списка, query деталей, mutation обновления. |
| Объём данных | `GET /v1/tasks` возвращает всю модель, включая `description`, хотя экран списка использует только `id`, `title`, `done`. | Клиент сам запрашивает только `id`, `title`, `done` для списка, поэтому лишних полей нет. |
| Обработка ошибок | Ошибка выражается HTTP-статусом и JSON-телом, например `404` и `{"error":"task not found"}`. | Ошибка приходит в поле `errors`; HTTP-статус часто остаётся `200`, поэтому клиент должен анализировать JSON-ответ. |
| Документирование | Endpoint и HTTP-методы легко описывать через таблицу маршрутов или OpenAPI. | Схема GraphQL сама показывает типы, query и mutation, но клиенту нужно понимать язык запросов. |
| Тестирование | REST удобно проверять через `curl`, `httptest` и статусы HTTP. | GraphQL удобно тестировать через отправку query/mutation и проверку полей `data` и `errors`. |
| Кэширование | Концептуально проще: разные URL и методы хорошо ложатся на стандартный HTTP-кэш. | Сложнее: endpoint один, поэтому чаще нужны persisted queries, client-side cache или кэширование на уровне данных. |
| Простота учебной реализации | Выше, потому что достаточно маршрутов, JSON и HTTP-статусов. | Ниже, потому что нужны схема, генерация `gqlgen` и резолверы. |
| Гибкость клиента | Ниже, потому что форму ответа в основном задаёт сервер. | Выше, потому что клиент выбирает поля под конкретный экран. |

## Итоговый вывод

В выбранном сценарии REST и GraphQL требуют одинаковое количество сетевых обращений: список, детали и изменение данных. Главное отличие проявляется не в числе запросов, а в точности возвращаемых данных. REST endpoint списка возвращает всю модель задачи, включая `description`, хотя экран списка это поле не использует. GraphQL позволяет запросить только `id`, `title`, `done`, поэтому лучше подходит для экранов с разным набором полей. При этом REST проще читать, тестировать через `curl` и анализировать по HTTP-статусам. GraphQL требует больше инфраструктуры: схемы, генерации кода и резолверов. Обработка ошибок в REST в учебном CRUD-сервисе выглядит понятнее, потому что статус `404` сразу отражает проблему. В GraphQL ошибка находится в поле `errors`, поэтому клиентская логика должна быть внимательнее. Для простой системы задач REST выглядит более практичным решением. GraphQL становится полезнее, когда у клиента много разных экранов и важно точно выбирать структуру ответа.

## Ответы на контрольные вопросы

1. **В чём принципиальное отличие REST и GraphQL?**

   REST строится вокруг отдельных HTTP-ресурсов и методов. Для различных операций обычно используются разные endpoint, например `GET /v1/tasks`, `GET /v1/tasks/{id}` и `POST /v1/tasks`.

   В GraphQL обычно используется единый endpoint, а клиент самостоятельно описывает структуру запроса и выбирает необходимые поля. В REST состав ответа чаще определяет сервер, а в GraphQL — клиент.

2. **Что такое over-fetching и under-fetching?**

   `Over-fetching` — это получение клиентом большего количества данных, чем ему требуется. Например, для списка задач нужны только `id`, `title` и `done`, но сервер также возвращает `description`.

   `Under-fetching` — это ситуация, когда одного запроса недостаточно для получения всех необходимых данных и клиенту приходится выполнять дополнительные запросы.

3. **Почему GraphQL позволяет клиенту точнее выбирать поля ответа?**

   В GraphQL клиент явно перечисляет поля, которые должны присутствовать в ответе. Например, для списка задач можно запросить только `id`, `title` и `done`, а для страницы подробной информации дополнительно запросить `description`.

   Благодаря этому сервер возвращает именно тот набор данных, который нужен для конкретного пользовательского интерфейса.

4. **Почему REST проще кэшировать стандартными средствами HTTP?**

   В REST каждый ресурс обычно имеет отдельный URL. Например, список задач может находиться по адресу `/v1/tasks`, а отдельная задача — по `/v1/tasks/t_001`.

   Такие запросы удобно кэшировать с использованием стандартных HTTP-заголовков и промежуточных proxy-серверов. В GraphQL разные операции часто отправляются на один endpoint и различаются телом запроса, поэтому стандартное HTTP-кэширование организовать сложнее.

5. **Чем отличается обработка ошибок в REST и GraphQL?**

   В REST результат операции обычно выражается через HTTP-статусы:

   * `400 Bad Request`;
   * `404 Not Found`;
   * `500 Internal Server Error`.

   В GraphQL сервер нередко возвращает статус `200 OK`, а сведения об ошибке помещает в поле `errors` внутри JSON-ответа. Поэтому GraphQL-клиенту необходимо анализировать не только HTTP-статус, но и тело ответа.

6. **В каких случаях REST оказывается более практичным решением?**

   REST часто удобнее для простых CRUD-сервисов, внутренних API и систем с заранее известной структурой данных. Его проще реализовать, проверять через `curl`, документировать с помощью OpenAPI и кэшировать стандартными средствами HTTP.

7. **В каких случаях GraphQL может дать преимущества?**

   GraphQL полезен, когда разным клиентам нужны различные наборы полей одних и тех же объектов. Например, мобильное приложение, веб-интерфейс и административная панель могут обращаться к одному API, но запрашивать разные данные.

   GraphQL также позволяет уменьшить избыточность ответов и предоставляет клиенту больше гибкости при формировании запросов.

8. **Почему корректное сравнение REST и GraphQL нужно проводить на одном и том же сценарии?**

   Если подходы решают разные задачи, сравнение будет необъективным. Например, нельзя сравнивать получение списка задач через REST с созданием задачи через GraphQL.

   REST и GraphQL должны работать с одинаковой моделью, одинаковыми данными и выполнять один пользовательский сценарий. Только в таком случае можно корректно сравнить количество запросов, объём данных и обработку ошибок.

9. **Какие сложности возникают при сопровождении GraphQL API?**

   GraphQL требует поддержки схемы, резолверов и сгенерированного кода. Необходимо контролировать глубину и сложность запросов, поскольку клиент может запросить слишком большой объём вложенных данных.

   Дополнительно усложняются кэширование, мониторинг и анализ ошибок, поскольку разные операции выполняются через один endpoint.

10. **Почему для учебных CRUD-сервисов REST часто оказывается проще?**

    Учебные CRUD-сервисы обычно содержат стандартные операции получения, создания, обновления и удаления записей. Для них REST предоставляет понятное соответствие между HTTP-методами, URL и выполняемыми действиями.

    Такие endpoint легко проверить через `curl`, а HTTP-статусы сразу показывают результат операции. Использование GraphQL в простом CRUD-проекте может добавить лишнюю сложность без существенных преимуществ.
