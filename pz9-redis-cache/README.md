# Практическая работа №9. Redis cache-aside для сервиса tasks

## Цель

Освоить подключение Redis как внешнего кэша к Go-сервису и реализовать стратегию cache-aside для чтения задачи по идентификатору.

## Задание

Сервис хранит задачи в in-memory репозитории, а Redis использует только как кэш. Для чтения `GET /v1/tasks/{id}` сервис сначала проверяет Redis по ключу `tasks:task:<id>`. При cache miss задача читается из репозитория и записывается в Redis с TTL и jitter. После `PATCH` и `DELETE` соответствующий ключ удаляется из кэша. Ошибки Redis логируются, но не ломают API.

## Запуск Redis

```bash
cd pz9-redis-cache/deploy/redis
docker compose up -d
docker compose ps
```

Redis будет доступен на `localhost:6379`.

## Запуск сервиса

```bash
cd pz9-redis-cache
go run ./cmd/server
```

По умолчанию сервис слушает `:8082`. Адрес можно изменить через `HTTP_ADDR`, адрес Redis через `REDIS_ADDR`.

## Проверка cache miss и cache hit

Первый запрос читает задачу из репозитория и кладёт её в Redis:

```bash
curl http://localhost:8082/v1/tasks/1
```

В логах ожидаются сообщения вида:

```text
cache miss: tasks:task:1
cache set: tasks:task:1 ttl: ...
```

Повторный запрос должен прочитать задачу из Redis:

```bash
curl http://localhost:8082/v1/tasks/1
```

В логах ожидается:

```text
cache hit: tasks:task:1
```

Проверить ключ напрямую:

```bash
docker exec -it pz9_redis_cache redis-cli GET tasks:task:1
docker exec -it pz9_redis_cache redis-cli TTL tasks:task:1
```

## Проверка PATCH и инвалидации

```bash
curl -X PATCH http://localhost:8082/v1/tasks/1 \
  -H "Content-Type: application/json" \
  -d '{"title":"Обновлённая задача","description":"Новый текст","due_date":"2026-01-22T00:00:00Z"}'
```

После изменения в логах ожидается:

```text
cache invalidated: tasks:task:1
```

Следующий `GET` снова даст `cache miss` и запишет свежие данные в Redis:

```bash
curl http://localhost:8082/v1/tasks/1
```

## Проверка DELETE и инвалидации

```bash
curl -X DELETE http://localhost:8082/v1/tasks/1
```

В логах ожидается:

```text
cache invalidated: tasks:task:1
```

Повторное чтение удалённой задачи вернёт `404 Not Found`:

```bash
curl -i http://localhost:8082/v1/tasks/1
```

## Проверка fallback при остановленном Redis

Остановить Redis:

```bash
cd pz9-redis-cache/deploy/redis
docker compose stop
```

Выполнить запрос:

```bash
curl http://localhost:8082/v1/tasks/2
```

Сервис должен вернуть задачу из in-memory репозитория. В логах будет ошибка Redis, например `redis read error` или `redis write error`, но API продолжит работать.

## Ответы на контрольные вопросы

1. **Что такое cache-aside?**

   `Cache-aside` — это стратегия кэширования, при которой приложение само управляет чтением и записью данных в кэш. Сначала сервис пытается получить данные из Redis. Если данные найдены, они возвращаются из кэша. Если данных нет, сервис обращается к основному хранилищу, возвращает данные клиенту и дополнительно записывает их в Redis.

2. **Почему Redis не должен быть источником истины?**

   Redis в этой работе используется только как ускоритель чтения. Основные данные должны храниться в основном хранилище, например в базе данных или in-memory репозитории. Если считать Redis источником истины, то при очистке кэша, истечении TTL или недоступности Redis приложение может потерять данные или начать работать неправильно.

3. **Зачем нужен TTL?**

   TTL задаёт время жизни записи в кэше. После истечения TTL ключ автоматически удаляется из Redis. Это нужно, чтобы кэш не хранил данные бесконечно и мог периодически обновляться из основного хранилища.

4. **Что такое jitter?**

   `Jitter` — это небольшой случайный разброс, который добавляется к TTL. Например, если базовый TTL равен 60 секундам, итоговый TTL для разных ключей может немного отличаться. Это помогает избежать одновременного истечения большого количества ключей.

5. **Почему одинаковый TTL для всех ключей может быть проблемой?**

   Если у большого числа ключей одинаковый TTL, они могут истечь почти одновременно. После этого много запросов сразу пойдёт в основное хранилище, что создаст резкий всплеск нагрузки. Jitter делает истечение ключей более равномерным.  

6. **Как должен вести себя сервис при недоступности Redis?**

   Сервис не должен падать или долго зависать. При ошибке Redis он должен записать предупреждение в лог и продолжить работу через основное хранилище. В этой работе данные при недоступном Redis всё равно возвращаются из in-memory репозитория.

7. **Почему кэш нужно инвалидировать после изменения данных?**

   После изменения или удаления данных старая версия объекта в кэше становится неактуальной. Если её не удалить, клиент может получить устаревшие данные. Поэтому после `PATCH` или `DELETE` соответствующий ключ Redis нужно сбрасывать.

8. **Чем кэширование одной сущности проще, чем кэширование списка?**

   Одну сущность проще кэшировать и инвалидировать, потому что у неё есть понятный ключ, например `tasks:task:1`. При изменении этой задачи достаточно удалить один ключ. Со списками сложнее: один объект может входить в разные списки, страницы и выборки, поэтому при изменении данных нужно понимать, какие именно ключи списка стали устаревшими.

9. **В чём смысл ключа вида `tasks:task:<id>`?**

   Такой ключ понятный, предсказуемый и единообразный. По нему сразу видно, что значение относится к сервису `tasks`, типу данных `task` и конкретному идентификатору задачи. Например, ключ `tasks:task:1` хранит задачу с id `1`.

10. **Почему Redis рассматривается как внешняя инфраструктурная зависимость?**

    Redis запускается отдельно от приложения и доступен по сети. Это не часть памяти Go-процесса, а отдельный сервис, от которого приложение зависит во время работы. Поэтому нужно учитывать сетевые ошибки, таймауты, недоступность Redis и корректную деградацию API.
