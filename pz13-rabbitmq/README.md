# Практическое занятие №13

## Тема и цель

Тема: подключение к RabbitMQ, отправка и получение сообщений.

Цель: реализовать учебный сценарий, в котором сервис `tasks` создаёт задачу через HTTP и публикует событие `task.created` в RabbitMQ, а отдельный `worker` получает сообщение, логирует его и подтверждает обработку.

## RabbitMQ, producer и consumer

RabbitMQ используется как брокер сообщений между HTTP-сервисом и фоновым обработчиком.

- `tasks` — producer: после успешного создания задачи публикует событие в очередь `task_events`.
- `worker` — consumer: читает сообщения из очереди, десериализует JSON, логирует данные события и отправляет подтверждение обработки.

## Формат события

```json
{
  "event": "task.created",
  "task_id": "t_001",
  "ts": "2026-03-26T10:20:30Z",
  "request_id": "pz13-001",
  "producer": "tasks",
  "version": "1.0"
}
```

`request_id` заполняется из заголовка `X-Request-ID`, если он передан.

## Надёжность обработки

Очередь `task_events` объявляется как durable, поэтому её описание сохраняется при перезапуске RabbitMQ.

Сообщения публикуются с `DeliveryMode: amqp.Persistent`, чтобы RabbitMQ сохранял их надёжнее, чем transient-сообщения.

Worker использует ручной `ack`: после успешной обработки вызывается `Ack(false)`. Если JSON некорректный, вызывается `Nack(false, false)`, и сообщение не возвращается в очередь.

Для consumer установлен `prefetch = 1`, чтобы worker получал не больше одного неподтверждённого сообщения одновременно.

## Проверка через Management UI

В RabbitMQ Management UI нужно открыть раздел `Queues and Streams` и убедиться, что существует очередь `task_events`. В карточке очереди видны количество сообщений, активные consumers, ready-сообщения и unacked-сообщения.

## Режим best effort

Публикация события работает в режиме `best effort`: задача создаётся независимо от результата отправки сообщения. Если RabbitMQ недоступен или публикация завершилась ошибкой, сервис пишет ошибку в лог, но клиент всё равно получает успешный ответ о создании задачи.

## Ответы на контрольные вопросы

1. **Зачем нужен брокер сообщений, если между сервисами можно использовать HTTP?**

   HTTP обычно используется для синхронного взаимодействия: один сервис отправляет запрос и ожидает ответ другого сервиса. Брокер сообщений позволяет организовать асинхронную работу, при которой producer отправляет сообщение в очередь и не ждёт завершения обработки. Это уменьшает связанность компонентов, позволяет выполнять фоновые задачи и сохранять сообщения при временной недоступности consumer.

2. **Что такое producer и consumer?**

   `Producer` — это компонент, который создаёт и публикует сообщения в очередь. В данной работе producer — сервис `tasks`, публикующий событие `task.created`.

   `Consumer` — это компонент, который получает сообщения из очереди и обрабатывает их. В данной работе consumer — отдельный worker.

3. **Почему сообщение нужно публиковать только после успешного создания задачи?**

   Если отправить событие до создания задачи, worker может получить сообщение о задаче, которая фактически не была сохранена. Это приведёт к несогласованности данных. Поэтому сначала должна успешно выполниться основная операция, а уже затем публиковаться событие `task.created`.

4. **Что такое ack и зачем он нужен?**

   `Ack` — это подтверждение успешной обработки сообщения. После получения `ack` RabbitMQ считает сообщение обработанным и удаляет его из очереди. Если подтверждение не было отправлено, брокер может повторно доставить сообщение consumer.

5. **Почему возможна повторная доставка сообщения?**

   Повторная доставка возможна, если consumer получил и обработал сообщение, но не успел отправить `ack`, например из-за остановки процесса или потери соединения. RabbitMQ считает такое сообщение неподтверждённым и может передать его повторно.

6. **Что делает параметр prefetch?**

   `Prefetch` ограничивает количество неподтверждённых сообщений, которые RabbitMQ может одновременно передать одному consumer. Значение `prefetch = 1` означает, что worker не получит следующее сообщение, пока не подтвердит обработку текущего.

7. **Чем durable queue отличается от non-durable queue?**

   Durable-очередь сохраняет своё определение после перезапуска RabbitMQ. Non-durable-очередь при остановке брокера удаляется. Чтобы повысить надёжность, durable-очередь обычно используется вместе с persistent-сообщениями.

8. **Почему JSON удобен как учебный формат сообщения?**

   JSON легко читать, выводить в логи и проверять вручную. В Go он поддерживается стандартным пакетом `encoding/json`, поэтому структуры можно удобно сериализовать перед публикацией и десериализовать при получении.

9. **Что означает режим best effort при публикации события?**

   В режиме `best effort` основная операция не отменяется при ошибке публикации события. В данной работе задача считается созданной, даже если RabbitMQ временно недоступен. Ошибка отправки сообщения фиксируется в логах, а клиент всё равно получает успешный ответ о создании задачи.

10. **Почему worker лучше выносить в отдельный процесс, а не смешивать с HTTP-обработчиками?**

    Отдельный worker не блокирует обработку HTTP-запросов и может масштабироваться независимо от основного сервиса. Его можно отдельно запускать, останавливать и перезапускать. Кроме того, сбой фоновой обработки не приводит к остановке HTTP-сервиса.
