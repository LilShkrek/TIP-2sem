# Практическое занятие №1

## Разделение монолита на 2 микросервиса. Взаимодействие через HTTP

Дисциплина: **Технологии индустриального программирования**  
Семестр: **2 семестр, 2025–2026 гг.**

---

## Цель занятия

Освоить базовый подход к переходу от монолитного backend-приложения к микросервисной архитектуре на основе разделения системы на два самостоятельных сервиса и организации их взаимодействия по HTTP.

---

## Основная идея практической работы

Нужно реализовать учебный проект из двух независимых Go-сервисов:

1. **user-service** — сервис пользователей.
2. **order-service** — сервис заказов.

Каждый сервис должен запускаться как отдельное приложение, иметь собственный `go.mod`, собственную точку входа `main.go`, собственные обработчики и собственные данные в памяти.

`order-service` должен уметь обращаться к `user-service` по HTTP, получать данные пользователя и формировать агрегированный ответ по заказу.

---

## Задачи

1. Изучить принцип разделения монолитного приложения на отдельные сервисы по зонам ответственности.
2. Спроектировать два независимых микросервиса на языке Go.
3. Реализовать HTTP-взаимодействие между сервисами.
4. Научиться передавать и обрабатывать JSON-данные при межсервисном обмене.
5. Реализовать сервис, который агрегирует собственные данные и данные внешнего сервиса.
6. Отработать запуск, тестирование и проверку взаимодействия двух микросервисов.
7. Проанализировать преимущества и ограничения микросервисного подхода на учебном примере.

## Сервис `user-service`

### Назначение

`user-service` хранит и отдаёт информацию о пользователях.

### Порт

Сервис должен запускаться на порту:

```text
8081
```

### Endpoint

```http
GET /users/{id}
```

### Модель пользователя

```go
type User struct {
    ID    int64  `json:"id"`
    Name  string `json:"name"`
    Email string `json:"email"`
}
```

### Данные в памяти

Можно использовать in-memory map, например:

```go
map[int64]User{
    1: {ID: 1, Name: "Иван Иванов", Email: "ivan@example.com"},
    2: {ID: 2, Name: "Мария Петрова", Email: "maria@example.com"},
    3: {ID: 3, Name: "Алексей Сидоров", Email: "alex@example.com"},
}
```

### Требования к поведению

- При запросе существующего пользователя сервис возвращает JSON с данными пользователя.
- При запросе несуществующего пользователя сервис возвращает `404 Not Found`.
- При некорректном `id` сервис возвращает `400 Bad Request`.
- При использовании неподдерживаемого HTTP-метода сервис возвращает `405 Method Not Allowed`.
- Ответы JSON должны иметь заголовок `Content-Type: application/json; charset=utf-8`.

### Пример проверки

```bash
curl http://localhost:8081/users/1
```

Ожидаемый ответ:

```json
{"id":1,"name":"Иван Иванов","email":"ivan@example.com"}
```

## Сервис `order-service`

### Назначение

`order-service` хранит заказы и умеет возвращать как обычный заказ, так и агрегированный ответ: заказ + данные пользователя из `user-service`.

### Порт

Сервис должен запускаться на порту:

```text
8082
```

### Endpoints

```http
GET /orders/{id}
GET /orders/{id}/full
```

### Модель заказа

```go
type Order struct {
    ID     int64   `json:"id"`
    UserID int64   `json:"user_id"`
    Item   string  `json:"item"`
    Price  float64 `json:"price"`
}
```

### DTO пользователя

```go
type UserDTO struct {
    ID    int64  `json:"id"`
    Name  string `json:"name"`
    Email string `json:"email"`
}
```

### Агрегированный ответ

```go
type OrderWithUser struct {
    Order Order   `json:"order"`
    User  UserDTO `json:"user"`
}
```

### Данные в памяти

Можно использовать in-memory map, например:

```go
map[int64]Order{
    101: {ID: 101, UserID: 1, Item: "Ноутбук", Price: 79990},
    102: {ID: 102, UserID: 2, Item: "Мышь", Price: 2490},
    103: {ID: 103, UserID: 1, Item: "Клавиатура", Price: 5990},
}
```

---

## HTTP-взаимодействие между сервисами

При вызове:

```http
GET /orders/{id}/full
```

`order-service` должен выполнить следующий сценарий:

1. Найти заказ у себя в памяти.
2. Взять `user_id` из заказа.
3. Выполнить HTTP-запрос в `user-service`:

```http
GET http://localhost:8081/users/{user_id}
```

4. Получить JSON с данными пользователя.
5. Собрать единый JSON-ответ:

```json
{
  "order": {
    "id": 101,
    "user_id": 1,
    "item": "Ноутбук",
    "price": 79990
  },
  "user": {
    "id": 1,
    "name": "Иван Иванов",
    "email": "ivan@example.com"
  }
}
```

---

## Требования к HTTP-клиенту в `order-service`

В `order-service` нужно реализовать отдельный клиент для вызова `user-service`, например файл:

```text
order-service/internal/order/client.go
```

Требования:

- использовать стандартный `net/http`;
- задать timeout, например `3 * time.Second`;
- обрабатывать ошибку сетевого запроса;
- обрабатывать статус `404 Not Found` от `user-service`;
- обрабатывать любые статусы, отличные от `200 OK`;
- корректно декодировать JSON-ответ пользователя.

---

## Требования к обработчикам `order-service`

### `GET /orders/{id}`

Должен вернуть только заказ:

```json
{"id":101,"user_id":1,"item":"Ноутбук","price":79990}
```

### `GET /orders/{id}/full`

Должен вернуть заказ вместе с данными пользователя:

```json
{
  "order": {
    "id": 101,
    "user_id": 1,
    "item": "Ноутбук",
    "price": 79990
  },
  "user": {
    "id": 1,
    "name": "Иван Иванов",
    "email": "ivan@example.com"
  }
}
```

### Ошибочные сценарии

- Если заказ не найден — вернуть `404 Not Found`.
- Если `id` заказа некорректный — вернуть `400 Bad Request`.
- Если `user-service` недоступен при вызове `/orders/{id}/full` — вернуть `502 Bad Gateway` или аналогичную ошибку, показывающую проблему внешнего сервиса.
- Если HTTP-метод не поддерживается — вернуть `405 Method Not Allowed`.

## Проверка работы

### Запуск `user-service`

Из папки `user-service`:

```bash
go run ./cmd/server
```

Ожидаемый лог:

```text
user-service started on :8081
```

### Запуск `order-service`

Из папки `order-service`:

```bash
go run ./cmd/server
```

Ожидаемый лог:

```text
order-service started on :8082
```

### Проверка `user-service`

```bash
curl http://localhost:8081/users/1
```

Ожидаемый ответ:

```json
{"id":1,"name":"Иван Иванов","email":"ivan@example.com"}
```

### Проверка обычного заказа

```bash
curl http://localhost:8082/orders/101
```

Ожидаемый ответ:

```json
{"id":101,"user_id":1,"item":"Ноутбук","price":79990}
```

### Проверка агрегированного ответа

```bash
curl http://localhost:8082/orders/101/full
```

Ожидаемый ответ:

```json
{
  "order": {
    "id": 101,
    "user_id": 1,
    "item": "Ноутбук",
    "price": 79990
  },
  "user": {
    "id": 1,
    "name": "Иван Иванов",
    "email": "ivan@example.com"
  }
}
```

### Проверка ошибки внешнего сервиса

1. Остановить `user-service`.
2. Выполнить запрос:

```bash
curl -i http://localhost:8082/orders/101/full
```

Ожидаемый результат:

- `order-service` не должен падать;
- должен вернуться статус `502 Bad Gateway` или похожая ошибка;
- в ответе должно быть понятно, что проблема связана с получением данных пользователя.

## Критерии готовности

Практическая работа считается выполненной, если:

- создано два отдельных Go-сервиса;
- у каждого сервиса есть собственный `go.mod`;
- `user-service` запускается на порту `8081`;
- `order-service` запускается на порту `8082`;
- `user-service` отдаёт пользователей по `GET /users/{id}`;
- `order-service` отдаёт заказы по `GET /orders/{id}`;
- `order-service` отдаёт агрегированный ответ по `GET /orders/{id}/full`;
- `order-service` реально обращается к `user-service` по HTTP;
- корректно обработаны ошибки `400`, `404`, `405` и ошибка недоступности внешнего сервиса;
- добавлен понятный `README.md` с запуском и проверкой;
- код отформатирован через `gofmt`;
- `go test ./...` и `go vet ./...` выполняются успешно в обоих сервисах.
